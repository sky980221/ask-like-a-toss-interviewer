# 서버 면접 질문 패턴

다음 패턴은 필요한 경우에만 선택적으로 사용한다. 가장 좋은 꼬리질문은 레포지토리의 실제 구현, 제공된 자료, 사용자가 공부한 주제와 직전 답변에서 자연스럽게 이어지는 질문이다. 모든 주제를 순서대로 묻거나, 지원자가 사용하지 않은 기술을 억지로 끌어오지 않는다. 레포지토리를 사용하는 경우 [레포지토리 기반 면접 지침](repository-interview-mode.md)을 함께 따른다.

## 입력별 질문 설계

### 포트폴리오·이력서가 있을 때

1. 프로젝트별로 문제, 기여, 기술 선택, 수치와 결과를 파악한다.
2. 면접 가치가 높은 주장 두세 개를 내부적으로 고르되 질문 목록을 사용자에게 미리 공개하지 않는다.
3. 가장 구체적인 주장 하나에서 시작해 실제 수행 여부와 판단 근거를 확인한다.
4. 답변이 충분하면 내부 원리와 운영 결과로 확장하고, 불분명하면 기여 범위와 측정 조건을 먼저 확인한다.
5. 자료의 문구와 답변이 다르면 공격적으로 단정하지 말고 차이를 설명해 달라고 요청한다.

### 공부한 주제로 시작할 때

1. “무엇인지”를 자신의 말로 설명하게 한다.
2. “왜 필요한지”와 적용하지 않아도 되는 조건을 묻는다.
3. 내부 동작이나 핵심 불변 조건을 설명하게 한다.
4. 유사한 선택지와 장단점을 비교하게 한다.
5. 짧은 시스템 상황에 적용하게 하고, 장애·확장·운영 조건을 하나씩 추가한다.
6. 마지막에는 처음 답변에서 무엇을 수정하겠는지 묻는다.

학습 주제 기반 면접에서는 프로젝트 경험이 없다는 이유만으로 감점하지 않는다. 대신 개념의 정확성, 추론 과정과 새로운 상황에 적용하는 능력을 평가한다.

## 핵심 질문 흐름

자료 기반 면접에서는 구체적인 프로젝트 주장으로 시작해 실제 운영 환경의 결과까지 확장한다. 학습 주제 기반 면접에서는 아래 흐름의 ‘주장과 근거’를 ‘개념 설명과 적용 조건’으로 바꿔 사용한다.

1. **주장과 근거** — 무엇이 느리거나, 안전하지 않거나, 신뢰할 수 없었는가? 어떤 지표나 장애가 이를 입증했는가?
2. **주도성과 기여도** — 지원자가 직접 결정하고 구현한 것은 무엇인가? 팀원이나 라이브러리가 담당한 것은 무엇인가?
3. **선택** — 왜 이 해결책이었는가? 프로젝트의 실제 규모에서 사용할 수 있었던 가장 단순한 대안은 무엇인가?
4. **동작 원리** — 어떤 스레드, 풀, 프록시, 트랜잭션, 행, 메시지, 헤더 또는 프로세스가 실제 동작을 수행하는가?
5. **실패** — 두 개의 의미 있는 작업 사이에서 프로세스가 종료되면 어떤 일이 발생하는가?
6. **확장** — 인스턴스가 두 개가 되고, 다시 수십 개의 서비스로 늘어나면 무엇이 깨지는가?
7. **정확성** — 중복, 순서, 동시성, 재시도와 부분 성공을 어떻게 처리하는가?
8. **운영** — 시스템을 어떻게 관측하고, 배포하고, 진행 중인 작업을 비우고, 복구하고, 디버깅하는가?

## 질문 경로 선택

지원자가 실제로 말한 경험을 출발점으로 삼는다. 예를 들어 캐시를 사용하지 않은 지원자에게 Redis 내부 구조부터 묻지 않는다. 대신 해당 시스템에서 캐시가 필요한지부터 확인하고, 지원자가 캐시 도입을 제안했을 때 선택과 동작 원리를 깊게 묻는다.

하나의 답변에서는 관련성이 가장 높은 질문 경로 한두 개만 선택한다. 충분히 검증한 뒤 다른 주제로 이동한다.

## 중요 주제별 질문 경로

### API와 도메인 설계

- 요구사항을 데이터 모델과 API로 어떻게 변환했는지 묻는다.
- 도메인 규칙, 검증 책임, 상태 전이와 실패 응답을 어디에서 처리하는지 확인한다.
- API 멱등성, 버전 관리, 페이지네이션과 하위 호환성은 실제 요구가 있을 때 확장한다.
- 프레임워크 계층이 아니라 비즈니스 책임을 기준으로 경계를 설명하게 한다.

### 데이터베이스와 영속성

- 데이터 모델, 조회 패턴과 인덱스 선택이 연결되는지 확인한다.
- 실행 계획, N+1, 페이지네이션, 대량 쓰기와 데이터 마이그레이션은 프로젝트 경험에 맞춰 묻는다.
- 정규화와 비정규화, 관계형 데이터베이스와 다른 저장소의 선택 기준을 확인한다.
- 트랜잭션 범위가 외부 API 호출이나 긴 작업을 불필요하게 포함하지 않는지 묻는다.

### 비동기 작업

- 요청 스레드, Executor 워커, 큐와 하위 서비스 호출을 구분하게 한다.
- 스레드 풀과 큐 크기를 무엇을 근거로 결정하고 검증했는지 묻는다.
- 제한 큐와 무제한 큐, 거부 정책, 역압과 과부하 응답을 확인한다.
- 프로세스가 종료된 뒤에도 무엇이 남는지, Graceful Shutdown이 실제로 무엇을 기다리는지 묻는다.
- 프로젝트와 답변에 필요한 경우에만 내구성 있는 메시징, 확인 응답, 재시도, 처리 불가능 메시지와 멱등성으로 확장한다.

### 트랜잭션과 데이터 정합성

- 데이터베이스 롤백, 프로세스 장애와 원격 시스템의 부수 효과를 구분하게 한다.
- 어떤 자원에 락을 걸며 락의 범위를 최소화한 이유를 묻는다.
- 주장한 경험의 깊이에 맞춰 MySQL/InnoDB 격리 수준, MVCC, 갱신 손실, 데드락과 재시도를 확인한다.
- 금전이나 외부 시스템에 영향을 주는 작업이라면 멱등성 키, 유일성 제약조건, 트랜잭셔널 아웃박스와 사후 대사를 묻는다.

### 캐시와 상태 관리

- 무엇을 캐시하며 원본 데이터의 소유자는 누구인지 묻는다.
- TTL, 무효화, 캐시 미스, 동시 갱신과 장애 시 동작을 확인한다.
- 캐시 스탬피드, 핫 키와 일관성 수준은 시스템 규모와 답변에 필요할 때만 확장한다.
- 세션이나 분산 락 용도로 사용했다면 만료와 소유권 검증까지 묻는다.

### 메시징과 이벤트 처리

- 동기 호출 대신 메시징을 선택한 이유와 전달 보장을 묻는다.
- 생산, 저장, 소비와 확인 응답 사이의 실패 지점을 순서대로 설명하게 한다.
- 중복, 순서, 재처리, 처리 불가능 메시지와 컨슈머 장애를 어떻게 다루는지 확인한다.
- 정확히 한 번 처리된다는 표현이 나오면 시스템 전체에서 실제로 무엇을 보장하는지 검증한다.

### 관측 가능성과 추적

- 일반 매개변수 대신 MDC나 추적 컨텍스트를 선택한 이유를 묻는다.
- ThreadLocal의 경계와 Executor 간 컨텍스트 전파를 확인한다.
- 비즈니스 메서드의 시그니처를 오염시키지 않으면서 HTTP나 메시징 경계를 넘어 추적 정보를 전달하는 방법을 묻는다.
- 로그, 메트릭과 트레이스를 구분하게 하고 구체적인 디버깅 순서를 요구한다.

### 성능과 용량 계획

- 병목을 추측이 아니라 지표, 프로파일링 또는 부하 테스트로 확인했는지 묻는다.
- 평균뿐 아니라 상위 지연 시간, 처리량, 오류율과 자원 사용량을 확인한다.
- 부하 테스트 모델이 실제 트래픽의 도착률, 동시성, 요청 크기와 의존 서비스 지연을 반영하는지 묻는다.
- 최적화 전후 결과와 새로 생긴 병목 또는 비용을 설명하게 한다.

### 과부하 보호

- 요청 속도 제한, 동시 실행 제한, 제한 큐, 서킷 브레이커와 부하 차단을 구분하게 한다.
- 429와 503 중 어떤 응답이 적절한지, 재시도 폭주 없이 클라이언트가 어떻게 재시도해야 하는지 묻는다.
- 시스템에 실제로 요청 속도 제어가 필요할 때만 토큰 버킷, 리키 버킷, 고정 윈도우와 슬라이딩 윈도우를 비교하게 한다.
- 다중 인스턴스 환경에서는 공유 상태, 원자성, 핫 키와 근삿값 제한 및 엄격한 제한의 차이를 확인한다.

### 배포와 종료

- 새로운 트래픽이 기존 인스턴스로 전달되지 않게 하는 방법과 진행 중인 작업을 안전하게 비우는 방법을 묻는다.
- Readiness, Liveness, PreStop 동작, SIGTERM 처리와 종료 제한 시간을 구분하게 한다.
- 직접 생성한 Executor와 백그라운드 워커가 종료 과정에 참여하는지 묻는다.

### 테스트와 변경 안전성

- 무엇을 단위 테스트, 통합 테스트, 계약 테스트 또는 부하 테스트로 검증했는지 묻는다.
- 정상 경로보다 경계값, 동시성, 재시도와 장애 복구를 어떻게 검증했는지 확인한다.
- 배포 전후 검증, 점진적 배포, 롤백과 데이터 호환성을 프로젝트 상황에 맞춰 묻는다.

## 이해의 전이 확인

지원자의 기존 경험을 그대로 암송하게 하는 데 그치지 않는다. 하나의 원리를 충분히 확인한 뒤에는 도메인이나 제약조건을 바꾼 짧은 상황을 제시해 이해를 전이할 수 있는지 본다. 원래 프로젝트가 이미지 처리였다면 문서 변환이나 알림으로, 커머스였다면 정산이나 재고로 바꿀 수 있다. 다만 새로운 상황은 원리를 검증하는 데 필요한 만큼만 사용하고, 지원자가 경험하지 않은 일을 했다고 가정하지 않는다.
